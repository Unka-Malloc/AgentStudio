# ADR 0014: Client Fingerprint and System Key Storage

## Metadata / 元数据

- Last updated: 2026-06-16
- Status: Accepted
- Scope: Client-local runtime process identity, client installation fingerprinting, system key storage, signed process requests, and capability binding context.
- Staleness check: Checked against current consolidated docs layout and referenced implementation evidence on 2026-06-16.

## Status
Accepted

## Context

Pact supports a client-managed local server runtime. The desktop client can build or install a `client-local-runtime` sidecar, start it on loopback, claim it with a one-time token, and then use process identity for privileged runtime operations.

The system needs to distinguish two related but different facts:

- **Secret possession**: the caller can use the process private key and capability key.
- **Client instance identity**: the caller claims to be a specific client installation/runtime instance.

If these are conflated, the server cannot distinguish key possession from the claimed client installation identity. The operating system Keychain/Keyring/DPAPI boundary owns key access policy. Pact records a stable client fingerprint so the server can bind issued identity packages and capability keys to a specific claimed client instance.

## Decision

Pact adopts a software-level **client fingerprint + system key storage** model.

1. The client generates the process Ed25519 private key locally. The private key is not generated by the server and is not sent to the server.
2. The client stores the process private key and issued capability key through the system secret backend where available. On macOS this is Keychain; non-macOS platforms use the configured system keyring backend or a degraded file fallback where implemented.
3. The client also generates a non-secret client installation fingerprint and stores it in the client data root. This fingerprint is separate from the private key.
4. During local runtime claim, the client sends the fingerprint with the process public key, `clientId`, `installationId`, default identity hash, and claim nonce.
5. The server signs the fingerprint into `ClientIdentityPackageV1` together with `serverId`, `serverTrustPin`, `packageId`, `processKeyId`, `processPublicKeyHash`, identity generation, and capability metadata.
6. Process identity request headers include the signed identity ids plus fingerprint headers. The canonical request string includes fingerprint fields when the package has them, so the request signature covers the instance identity claim.
7. The server rejects signed requests when fingerprint headers are missing, malformed, or do not match the active signed identity package.
8. Capability Binding Guard includes the fingerprint context in its HMAC-bound record: `fingerprintId`, `machineInstanceId`, `appInstanceId`, `runtimeInstanceId`, and `clientFingerprintHash`.
9. Existing sealed binding guard state remains readable through a legacy state-root check; after a successful save it is rewritten with the expanded context shape.

## Fingerprint Shape

The client fingerprint is not a secret. It is a stable client-instance descriptor with these fields:

- `fingerprintId`
- `machineInstanceId`
- `appInstanceId`
- `runtimeInstanceId`
- `fingerprintHash`

`fingerprintHash` is derived from the fingerprint version and the four instance ids. It is used as a compact binding/audit value, not as a secret.

## Security Boundary

This ADR deliberately separates responsibilities:

- Pact verifies that a caller holds the process private key/capability key and presents the signed fingerprint bound to the active server package.
- The operating system controls who can read or use the stored secret material.
- Pact binds authorization to the active server package, process public key, capability key, and signed client fingerprint.
- Original-device guarantees require a hardware-anchored or externally attestable trust root, such as hardware-backed keys, TPM/Secure Enclave, platform attestation, a helper under a separate OS identity, or a remote trust service.

## Consequences

- Process-identity-required operations must present the process signature, capability key, active package id, and signed fingerprint context together.
- Fingerprint mismatch is a first-class denial reason for process-identity-required operations.
- The browser console continues using session/CSRF. UI actions requiring process identity must be proxied through the client daemon/CLI rather than exposing the private key to JavaScript.
- Client fingerprint files must be treated as integrity-relevant but non-secret state.
- System key storage failures may still use degraded fallback where the platform implementation allows it; degraded fallback must be observable through identity status.
- Strong non-forgeable device identity requires a hardware-anchored or externally attestable trust root.

## Verification

Current focused verification commands:

```bash
cargo test --manifest-path client-cli/Cargo.toml process_identity -- --nocapture
node server/scripts/verify-process-identity.mjs
node server/scripts/verify-capability-binding-guard.mjs
```

The verification covers identity package signing, canonical request construction, nonce replay, fingerprint mismatch rejection, capability binding context matching, and compatibility with legacy binding guard sealed state.
