# ADR 0011: ServiceHub Registration Is Control Plane Only

## Metadata / 元数据

- Last updated: 2026-06-14
- Status: Accepted
- Scope: ServiceHub registration authority, external-service manifests, egress, secrets, adoption, and runtime invocation boundaries.
- Staleness check: Scanned on 2026-06-14; ServiceHub production claims are covered by current external-service, security, and MCP verification gates.

## Status
Accepted

`pact.serviceHub` is the MCP outlet for discovering and invoking already registered external services. It is not an external-service registration surface. Ordinary MCP agent grants must not create, update, refresh, delete, or bind secrets for external service registrations through `pact.serviceHub`, because that would let an agent mint arbitrary egress endpoints and turn Pact into an SSRF, data exfiltration, or tool-poisoning proxy.

External service registration remains an operator/admin control-plane action. The registration path may provide templates, linting, dry-run plans, egress policy preflight, upstream contract verification, and generated examples for ease of use, but persistence requires an operator/admin grant, explicit confirmation, secretRef binding, policy evaluation, and audit.

Registration must use server-maintained typed templates instead of bare URL registration. The first required template families are HTTP/HTTPS raw MCP passthrough, HTTP JSON compile, HTTPS JSON compile, and OpenAI-compatible model gateway forwarding. Templates produce reviewable `pact.external-service.config` manifests and validation plans; they do not create runtime tools by themselves.

Raw MCP passthrough in ServiceHub is HTTP/HTTPS only. ServiceHub must not register, start, or forward stdio MCP processes, command transports, cwd/env launch descriptors, or local-process MCP bridges as external services. Local stdio MCP can expose local configuration, environment variables, filesystem access, shell authority, and user identity, so it is outside the external-service-address-to-MCP forwarding contract. A local MCP capability must first be exposed by its owner as a governed HTTP/HTTPS MCP endpoint before ServiceHub can register it.

Raw MCP passthrough is tools-only. ServiceHub uses upstream `initialize`, `tools/list`, and `tools/call` to produce governed Pact tools, but it does not expose upstream resources, prompts, roots, sampling, elicitation, logging, arbitrary notifications, or client callbacks to downstream agents. Non-tool MCP data is handled only as untrusted tool result data through Output Governance and governed asset references.

Ordinary MCP agents may access the template catalogue and sanitized draft/dry-run operations through `pact.discovery` so they can help users prepare manifests. Those read-only discovery operations must not persist registry entries, bind secret values, refresh tool caches, delete services, or make a draft callable.

Discovery dry-run is static only. It must not contact upstream services, fetch remote specs, probe tokens, run MCP discovery, or scan DNS/ports. Live contract verification is reserved for operator/admin control-plane operations with egress preflight, explicit confirmation, timeout, rate limit, audit, and read-only probe limits.

ServiceHub invocation is manifest-bound. Agent input may populate only schema-validated business fields declared by the registered tool mapping. URL, method, path, authorization, cookies, arbitrary headers, proxy, TLS, timeout, retry, and secret material are controlled by the manifest, policy, and server-side secretRef injection.

Mappings and transforms are sandboxed. Request mappings, response mappings, error mappings, body templates, and transforms in external-service manifests are limited to a deterministic declarative safe subset. They must not execute code, load plugins, access filesystem/network/environment/process state, read secrets directly, or dynamically override URL, method, auth, headers, proxy, TLS, or other transport controls. Mapping evaluation is bounded by expression, template, output, depth, array, CPU, time, memory, and recursion limits; failures are normalized and audited without logging rendered request bodies or intermediate values.

Outbound payloads are governed before any upstream call. Passing the registered tool input schema is not sufficient to send data to an external service; Pact must also enforce allowed outbound fields, data classes, size, JSON depth, text length, asset/ref handling, and redaction policy. Secrets, hidden prompts, Pact internal instructions, raw workspace files, raw AgentLibrary content, unauthorized data classes, unauthorized asset refs, debug context, and full conversation transcripts are blocked by default. Receipts and audit records capture outbound governance decisions and summaries, not raw request bodies.

External service credentials are bound only through the operator/admin control plane. Templates and agent-visible drafts may expose secret slots, suggested secretRef placeholders, missing-credential diagnostics, and configured/missing status, but ordinary MCP agents must not submit, read, update, rotate, or rebind secret values. Persisted manifests store only secretRef references and redacted credential metadata; runtime resolves SecretStore values server-side and injects them only into the manifest-declared auth or transport location. Secret rotation, revocation, or scope downgrade invalidates related upstream sessions, auth context, discovery caches, and health state.

ServiceHub egress is default-deny. Registrations must explicitly declare allowed protocol, host, port, and address classes. Production rejects loopback, private, link-local, cloud metadata, container/orchestration management, and local management networks unless a local service exception is operator/admin approved with owner, purpose, expiry, and audit. Runtime checks must validate resolved IPs and revalidate redirect targets.

Upstream-discovered tool metadata is untrusted. MCP passthrough `tools/list` results must pass a ServiceHub Tool Adoption Gate: namespace tool identities, sanitize descriptions and instructions, validate JSON Schema against a safe subset, allowlist annotations, fingerprint versions, show operator-visible diffs, and hide new or riskier tools until explicitly adopted.

ServiceHub changes are promoted by version. Refreshes and manifest changes create candidate catalog versions with diffs, fingerprints, verification evidence, grant projection impact, and rollback plans. They do not mutate the active production catalog until an operator/admin promotes them. The previous active version remains available for rollback, and promote/rollback invalidates related sessions, caches, health state, and projection versions with audit evidence.

ServiceHub visibility is grant-projected. Adoption does not make a tool visible to every agent; the current grant must allow the service id, operation id, risk level, tenant/workspace, egress policy, data class, and configured secret binding. Unauthorized services and tools are hidden from `tools/list` by default, and every invocation still performs real-time authorization against the latest grant and policy state.

ServiceHub catalog visibility is stable across upstream availability changes. Temporary upstream outages, timeouts, DNS failures, degraded health, or open circuit breakers must not automatically remove tools from `tools/list` or rewrite adopted schemas. Availability state controls invocation behavior: Pact returns standardized upstream unavailable/degraded/circuit-open errors with retry hints and audit references, uses circuit breakers to fail fast and prevent retry storms, and restores healthy state only after controlled health or contract recheck.

ServiceHub resources are quota-managed and bulkheaded. Calls are isolated and budgeted by service, operation, tenant/workspace, grant/subject, auth binding, upstream host, transport class, and model gateway. Rate, concurrency, queue, connection, worker, byte, stream event, retry, token, and cost budgets have hard limits. A single upstream, agent, tenant, or model gateway cannot exhaust global workers, connection pools, stream buffers, or upstream billing. Limit decisions are normalized, audited, and included in receipts without logging request or response content.

ServiceHub errors are taxonomy-managed. External-service invocation never exposes raw upstream HTTP bodies, MCP errors, provider exceptions, network details, stack traces, or debug payloads to downstream agents. Pact returns stable error envelopes with Pact-owned codes, redacted messages, retryability, optional bounded retry-after hints, unknown-outcome markers, and audit/receipt references. Retry hints are derived from ServiceHub policy, idempotency, ledger attempts, circuit state, and quota state; upstream retry headers are advisory input only. Unauthorized, unadopted, disabled, or grant-invisible services use non-enumerating errors by default.

Every ServiceHub invocation has a server-enforced deadline and concurrency lease. Agents cannot override timeout, deadline, lease TTL, concurrency limits, or cancellation semantics through tool input. Client disconnects, request cancellation, deadline expiry, or shutdown may propagate best-effort upstream aborts, but side-effecting operations become unknown external outcomes unless Pact can prove the upstream did not execute them. Timed-out or abandoned calls release local leases, update circuit breaker evidence, and enter orphan cleanup or reconciliation rather than silently completing in the background.

Side-effecting ServiceHub tools require reconciliation and recovery. Safe-write, repair-write, destructive, or explicitly side-effecting tools cannot become active unless their manifest declares an idempotency scope, read-only status query, reconciliation operation, compensation operation, or operator recovery workflow. Unknown external outcomes create recovery records, block automatic replay, and expose only redacted recovery status to authorized agents. Recovery operations remain manifest-bound, authorized, egress-governed, audited, and output-governed ServiceHub calls.

Streaming responses are governed and backpressured. ServiceHub must not raw-passthrough streamable HTTP, SSE, HTTP chunked, model gateway streams, or MCP stream chunks to downstream agents. Each chunk or event is subject to event-type allowlists, byte/time/rate/buffer limits, cancellation, partial-result policy, and Output Governance before it is emitted. Backpressure must limit upstream reads or fail with a governed streaming error; partial results are returned only as governed chunks or asset references.

Every ServiceHub invocation emits a redacted external call receipt. The receipt captures service/catalog/operation identity, grant and tenant/workspace context, risk, egress decision, mapping sandbox decision, outbound governance decision, quota/bulkhead decision, error taxonomy decision, reconciliation decision, streaming/backpressure decision, secretRef fingerprint, deadline/lease, retry and circuit state, upstream status class, output governance decision, redaction summary, asset references, unknown-outcome flag, recovery status, and audit reference. It must not contain raw secrets, headers, cookies, URL queries, request or response bodies, mapping intermediate values, raw stream chunks, provider debug traces, stack traces, or internal paths.

ServiceHub production promotion is blocked by a machine-verifiable Production Verification Matrix. Production profiles, external-service templates, and candidate catalog versions must provide passing evidence for the stable outlet set, removal of legacy `pact.knowledge` and `pact.call`, HTTP/HTTPS-only raw MCP transport, static template dry-run, manifest-bound invocation, Mapping Sandbox, Outbound Payload Governance, egress SSRF/DNS-rebinding/redirect protection, SecretStore-only credential injection, Tool Adoption Gate, Grant Projection, MCP Capability Firewall, Quota And Bulkhead, Error Taxonomy and Retry Hint, Reconciliation and Recovery, health/circuit behavior, deadline/cancellation/unknown-outcome handling, Streaming And Backpressure, versioned promotion and rollback, Output Governance, and external-call receipt redaction. Missing or failing evidence prevents promote and prevents the affected tools from entering downstream `tools/list`.

External MCP passthrough session state is isolated by default. Pact may reuse low-level connection pools, but initialized upstream MCP sessions, cursors, pagination tokens, conversation ids, and tool auth context are scoped by service id, Pact grant or subject, workspace or tenant, and auth binding. Grant revocation, secretRef rotation, workspace/tenant unbinding, or service disable invalidates the related upstream sessions. Shared session resources are allowed only when the upstream is verified stateless and the manifest explicitly marks it `sharedSessionSafe=true`.

ServiceHub outputs are governed before returning to agents. Raw upstream responses, headers, cookies, redirects, provider debug traces, internal paths, private object ids, stack traces, binary payloads, and oversized content must not be returned inline. Pact returns redacted JSON/text projections or governed asset references subject to AgentLibrary/SharedSpace authorization.

ServiceHub retry is opt-in. Read-only idempotent operations may retry under explicit policy. Side-effecting operations default to one attempt and require idempotency keys, ledger attempt/fence evidence, and explicit retry policy before any retry. Ambiguous timeout or disconnect outcomes are recorded as unknown external outcomes and must not be blindly replayed.
