# ADR 0007: Pact Work Queue Primitive Contract

## Metadata / 元数据

- Last updated: 2026-06-13
- Status: Current maintained document
- Scope: ADR 0007 - Pact Work Queue Primitive Contract.
- Staleness check: Created on 2026-06-12 during the NATS JetStream queue capability absorption design discussion.

## Status
Accepted

## Context
Pact needs a general-purpose task queue for platform capabilities and private-cloud production deployment. NATS JetStream is a useful reference for durable work-queue capabilities such as acknowledgement, redelivery, max delivery, pull delivery, and push delivery, but Pact should not expose NATS stream, subject, or consumer concepts as its internal platform contract.

The queue belongs to the platform infrastructure layer. It must remain separate from upper-layer application services: the queue owns scheduling state, while business state, workflow history, checkpoints, payloads, and results remain with the owning capability.

## Decision
1. **Pact-owned primitive contract**: Pact will define a stable `Pact Work Queue` primitive contract around `enqueue`, `claim`, `ack`, `nack`, `progress`, `term`, `recover`, `deadLetter`, and `inspect`. Backends may change, but these internal primitives and their state-machine semantics must not change except for lightweight adapter mapping.
2. **Broker-neutral API**: Pact will absorb selected NATS JetStream queue capabilities, but it will not expose NATS streams, consumers, subjects, ack subjects, or deliver policies as upper-layer contracts.
3. **Scheduling-only ownership**: A `Work Item` is the smallest queue-owned scheduling unit. It carries a lightweight envelope and stable references to owner, operation, payload, job, or workflow activity. The queue does not own large payloads, business results, workflow history, checkpoints, or domain status.
4. **Store contract and default backend**: `Pact Work Queue Store` is the source of truth for queue scheduling state. The default adapter uses SQLite WAL for high-performance single-node private-cloud deployment, but the `Work Queue Store Adapter` contract must allow later replacement by another database or broker without changing Pact's internal primitives.
5. **SQLite single-writer path**: The default SQLite WAL adapter uses one queue engine write path for durable queue mutations. Peers may contribute delivery or execution capacity, but they must not directly write queue projections or journals. A future adapter may support multiple writers only if it proves equivalent atomic claim, lease fencing, journal, and projection semantics.
6. **Durable commit before success**: Queue state changes must be durably committed before the corresponding queue operation reports success. `enqueue`, `claim`, `ack`, `nack`, `progress`, `term`, recovery transitions, and `deadLetter` cannot acknowledge success while accepted state exists only in volatile memory.
7. **Journal plus projection**: Every scheduling transition must be appended to `Queue Transition Journal`, and the current `Queue State Projection` used by high-performance claim, inspection, and metrics queries must be updated in the same durable transaction. Projections and verified snapshots may accelerate recovery, but replay from the journal must remain authoritative for verification.
8. **Provable state machine**: Queue scheduling state is a finite, explicit state machine. The initial accepted states are `pending`, `delayed`, `leased`, `dead_letter`, `fallback_review`, `acked`, and `terminated`. `acked` and `terminated` are terminal. `dead_letter` is scheduling exhaustion and does not mean the business object failed. `fallback_review` is an internal safe review state for fallback failures. Illegal transitions must fail closed.
9. **Core legal transitions**:
   - `enqueue`: none -> `pending` or `delayed`.
   - `claim`: `pending` -> `leased`.
   - `progress`: `leased` -> `leased` for the current valid lease only.
   - `ack`: `leased` -> `acked` for the current valid lease only.
   - `nack`: `leased` -> `pending`, `delayed`, or `dead_letter` according to deterministic retry policy.
   - `lease_expired`: `leased` -> `pending`, `delayed`, or `dead_letter` according to deterministic retry policy.
   - `delay_matured`: `delayed` -> `pending`.
   - `term`: `leased` -> `terminated` for the current valid lease only.
   - `fallback_failed`: `leased` -> `fallback_review` after bounded fallback retries fail.
   - `fallback_review_retry`: `fallback_review` -> `pending`, `delayed`, `dead_letter`, or `terminated` through governed fallback review handling.
   - `recover`: reconstructs projection from journal and verified snapshots; any recovery-created scheduling transition must also be journaled.
10. **At-least-once delivery**: The queue provides at-least-once delivery. Upper-layer capabilities must use idempotency keys, operation identifiers, checkpoints, or business state machines to prevent duplicate side effects.
11. **Lease fencing**: `claim` creates a lease identity. `ack`, `nack`, `progress`, and `term` must present the current valid lease identity. Stale workers, expired leases, redelivered attempts, and terminal work items must fail closed.
12. **Dedupe and isolation**: Enqueue idempotency is scoped by `queueDefinitionId + structuredScope + dedupeKey`. Scheduling isolation uses the trusted queue definition identity, normalized scope fields, and optional `concurrencyKey`; a `concurrencyKey` prevents concurrent claims for work items that must not run in parallel without serializing the entire queue.
13. **Scheduling order, not global FIFO**: Claim order is deterministic and indexable, normally based on priority, availability time, creation time, and work item identity. Pact does not promise global FIFO completion order because concurrency, retry, delay, and lease expiry can change execution order.
14. **Pull and push delivery**: Pact supports both pull claim and push dispatch semantics. Push dispatch must first perform the same durable claim and lease transition, then deliver the leased work item to a worker. Push and pull share the same acknowledgement, retry, progress, lease expiry, and dead-letter state machine.
15. **Lightweight worker runtime**: `Queue Worker Runtime` is the adapter between leased work item envelopes and business handlers. It resolves payload references through owning services, invokes handlers, and converts handler outcomes into queue primitives without exposing direct queue store or transition journal access. It must remain an adapter, not a business job framework or workflow engine.
16. **Handler outcome vocabulary**: Business handlers return a small structured outcome vocabulary such as `complete`, `retry`, `defer`, `terminate`, and `progress`. The Queue Worker Runtime translates those outcomes into queue primitives. Thrown errors are classified through queue policy and optional error explanation adapters rather than becoming queue state directly.
17. **Cooperative worker cancellation**: The Queue Worker Runtime may pass a cancellation signal to business handlers for timeout, manual cancellation, service shutdown, or runtime policy. Pause and drain do not imply cancellation. `term` is a scheduling transition and only becomes handler cancellation when the runtime explicitly supports and journals that cooperative path.
18. **Delivery subscription and worker group**: Push delivery uses Pact `Delivery Subscription` records, not NATS consumers. A `Worker Group` is a competing-consumer group: a work item can be leased to at most one worker in the group at a time. Queue delivery does not imply broadcast fanout.
19. **Route uniqueness**: A work item must resolve to at most one active delivery route unless fanout is explicitly modeled by creating separate work items or a dedicated fanout primitive. Overlapping push subscriptions must be rejected or proven non-overlapping.
20. **Peer-first backpressure**: Push dispatch must check local and eligible peer delivery capacity before creating a durable lease. When a route or worker group is saturated, Pact should first use compatible queue peers to share pressure under the same primitive contract and policy version. If no eligible capacity exists, it must avoid claiming new work instead of holding leased work in an in-memory dispatch buffer. If a durable claim succeeds but dispatch fails, the failure must be journaled and resolved through a legal retry or delay transition.
21. **Peer eligibility**: A peer can receive scheduling pressure only when it matches the same queue definition id, structured queue scope, delivery route, worker group or equivalent capacity pool, primitive contract version, policy version, authorization boundary, health status, and capacity checks. Peer selection must be recorded as an adopted queue decision and must not route work into an independent queue owner.
22. **Optional error explanation**: Queue error explanation is an assembled optional capability. Business services may register structured error metadata. Advisory explanations may be returned to upper layers, but free-form text cannot drive state transitions. Any retry hint that affects scheduling must be structured, deterministic, and journaled as the adopted decision.
23. **Deterministic replay boundary**: Non-deterministic scheduling decisions are made only during original execution and must be recorded as adopted structured decisions in the transition journal. Replay must not recalculate jitter, call live error explanation, reselect delivery routes, or reinterpret policy; it rebuilds projection from recorded decisions and verifies them against the state machine and recorded policy version.
24. **Versioned policy**: Retry, backoff, lease, route, concurrency, and related scheduling policies must have immutable policy versions. Queue policy changes affect future decisions only. Historical transition replay uses the policy version recorded with the adopted decision and must not reinterpret history through the current live policy.
25. **Default and custom scheduling policy**: Pact provides a default fairness policy for queue, scope, worker group, quota, rate, priority, and in-flight control. Custom scheduling policies are allowed, but they must be assembled through the project's policy management module, compile business semantics into structured deterministic scheduling decisions, carry policy versions, and record adopted decisions in the transition journal.
26. **Lazy time materialization**: Time-driven transitions such as `lease_expired` and `delay_matured` may be materialized when claim, push dispatch, recovery scan, or the persistence daemon observes them. They are not required to be committed at the exact wall-clock instant. Once materialized, the adopted time, reason, and policy version must be recorded in the transition journal, and replay must not create historical time transitions from the current clock.
27. **Journal retention and tiering**: Queue transition journal segments may be compacted, tiered, or archived under explicit retention policy, but snapshots and current projections cannot silently replace required traceability. Non-terminal work items must keep a replayable transition chain.
28. **Governed management operations**: Administrative and DevOps actions such as pause, resume, drain, requeue, move-to-dead-letter, archive, and retry-dead-letter must go through the Work Queue Primitive Contract and create legal journaled transitions. Management APIs must not directly mutate queue projection rows or bypass lease fencing and terminal-state rules.
29. **Pause and resume semantics**: Pause applies to a queue, scope, or subscription by preventing new pull claims and push dispatch. It must not preempt existing leases or block valid `ack`, `nack`, `progress`, or `term` operations from already leased work. If leased work later fails, expires, or becomes retryable, pause prevents the next delivery until resume.
30. **Drain semantics**: Drain stops new delivery for a queue, scope, or subscription and waits for existing leases to finish or reach an explicit timeout outcome. Drain is not task cancellation; timeout handling such as termination, dead-lettering, or remaining paused must be explicitly selected and journaled.
31. **Proof obligations**: Production queue semantics require a documented transition table, invariant list, transition journal replay, projection rebuild, crash/recovery tests, concurrent claim tests, lease expiry/redelivery tests, and randomized queue smoke tests. Randomized tests may explore every legal and illegal operation shape the state machine can contain, but successful execution must never accept or produce an impossible scheduling state.
32. **Module ownership**: The Pact Work Queue implementation belongs under `server/platform/common/resource-management/work-queue` as platform infrastructure resource management. Existing application job managers, including the current JobManager capability, should adapt to the queue through handlers and references instead of owning bottom-layer queue semantics.
33. **Adapter conformance gate**: Every `Work Queue Store Adapter` and delivery adapter must pass the shared Work Queue Conformance Suite before being considered compatible. The suite must cover the transition table, illegal-transition fail-closed behavior, journal replay, projection rebuild, concurrent claim, lease fencing, crash/recovery, and randomized smoke tests.
34. **Scheduling observability boundary**: Queue observability exposes scheduling metrics and diagnostics such as pending, leased, delayed, dead-letter, claim latency, acknowledgement latency, redelivery, lease expiry, backpressure, and peer handoff. Business success rates, business failure reasons, and domain execution duration remain with the owning application capability.
35. **Dedicated queue database**: The default SQLite WAL implementation uses a dedicated Work Queue Store database and migration set owned by `server/platform/common/resource-management/work-queue`. Current JobManager file metadata, payload, and result files must not be reused as the queue scheduling fact source.
36. **Terminal retention boundary**: `acked` and `terminated` queue projections may be archived or cleaned according to terminal retention policy, while journal traceability remains governed by Queue Journal Retention. Non-terminal work items must keep replayable history and must not be reduced to projection-only or snapshot-only records.
37. **Queue operation governance**: `enqueue`, delivery subscription configuration, pause, drain, retry-dead-letter, and other management operations must pass through Operation, Authorization, and Policy governance. Worker `ack`, `nack`, `progress`, and `term` are accepted through lease fencing and Queue Worker Runtime binding, not exposed as unrestricted business-service APIs.
38. **Legacy job history compatibility**: Existing JobManager history remains queryable as upper-layer business history, but it is not forcibly migrated into the new queue transition journal. New scheduling facts after adoption are written through Pact Work Queue, while old job metadata and results keep their existing historical meaning.
39. **Journal data minimization**: Queue Transition Journal entries store scheduling fields, stable references, structured error codes, adopted policy decisions, operation identifiers, actor metadata, and redacted diagnostics only. They must not store large payloads, raw file content, full business results, unredacted exception stacks, or sensitive business data.
40. **Concurrency key fairness**: Default scheduling policy must protect against one concurrency key monopolizing queue capacity. Implementations should support per-key in-flight limits, age boost, scope fairness, or policy-defined weights while preserving local serialization for keys that require it.
41. **Operation ledger relationship**: Queue Transition Journal is the replay source for queue scheduling state. Operation Ledger records governed operation intent, authorization, actors, policy decisions, and key correlations. The two link through `operationId` and related identifiers but do not replace each other.
42. **Verified snapshots**: Queue snapshots must record journal range, schema version, policy version set, and digest, and must be verified by replay. Recovery may start from a verified snapshot as an acceleration point, but it must validate subsequent journal entries and must not skip state-machine checks.
43. **External broker adapter boundary**: NATS JetStream or another broker may be used only as a Work Queue Store Adapter or delivery adapter implementation detail. Pact's upper-layer API, primitive contract, journal/projection model, replay behavior, and conformance obligations remain unchanged.
44. **Governed schema migration**: Queue schema, projection, snapshot, and journal migrations must run through governed migration tooling. A migration is not acceptable unless it proves that projections can be rebuilt from the journal and verified snapshots before and after the change.
45. **Randomized coverage surface**: Randomized queue smoke tests must cover pull, push, pause, drain, peer backpressure, lease expiry, delay maturity, dedupe, concurrency keys, and illegal `ack`, `nack`, `progress`, and `term` operations. Testing only enqueue, claim, and ack happy paths is insufficient.
46. **API facade boundary**: Pact should start with internal module APIs plus Tool/Console management surfaces. Future HTTP, MCP, or RPC exposure is a governed facade over Pact queue primitives, not a separate protocol or broker-native API.
47. **Unified time source**: Pact Work Queue must use a mandatory unified, injectable time source for adopted times, availability, lease expiry, delay maturity, retry scheduling, and journal timestamps. Queue implementation code must not scatter direct wall-clock calls such as `Date.now()`, because tests, replay, and proof require controlled time.
48. **Global queue identities**: Queue identities such as `workItemId`, `leaseId`, `journalEntryId`, and `subscriptionId` are generated by the queue module's identity generator. Production identifiers must be globally unique, use at least UUIDv7 semantics, and may combine a distributed uniqueness algorithm. Tests may inject deterministic generators while preserving the same identity contract.
49. **Controlled store optimization**: SQLite WAL performance optimizations may use prepared statements, batch transactions, short transactions, covering indexes, checkpointing, and compaction. Control and proof are higher priority than throughput: no optimization may acknowledge success before durable commit or bypass the queue state machine, transition journal, or primitive contract.
50. **Worker identity boundary**: Worker identifiers are registered or issued by Queue Worker Runtime. They support observation, capacity, binding, and audit, but acknowledgement authority remains lease-fenced; workers must not gain queue mutation authority by self-reporting a `workerId`.
51. **Payload resolution boundary**: Queue Worker Runtime resolves `payloadRef` through the owning capability or service. Pact Work Queue stores and passes references but does not directly read business files, business databases, or payload internals.
52. **Failure diagnostic minimization**: Queue journal entries retain structured failure diagnostics such as `errorCode`, `errorClass`, `retryHint`, and redacted messages. Full exceptions, stack traces, and business diagnostics remain in the owning capability logs or result stores and are linked by reference.
53. **Worker registration lifecycle**: Queue Worker Runtime records worker registration, heartbeat, capacity snapshots, and push or peer eligibility for dispatch decisions and observability. These records are not the source of truth for work item state and must not be required to replay queue scheduling history.
54. **Lease timeout policy**: Pact may use the JetStream-style 30 second acknowledgement wait as the default lease timeout baseline, but queue policy, delivery subscription, or enqueue options may override it. The adopted timeout must be recorded with claim decisions so replay verifies the lease behavior without reading current configuration.
55. **Finite max attempts**: Pact Work Queue must use a safe finite default for maximum delivery attempts instead of infinite retry. The default may be tuned by policy, and adopted max-attempt values must be journaled before retry exhaustion or dead-letter decisions depend on them.
56. **Retry backoff**: Default retry scheduling uses deterministic capped exponential backoff. If jitter is enabled, the adopted delay must be recorded in the transition journal; replay verifies the recorded delay and does not recompute randomness.
57. **Dead-letter retry**: Retrying dead-letter work is an explicit governed management operation. It must journal actor, reason, policy version, and adopted scheduling decision, and dead-letter work must not be silently retried automatically.
58. **Progress heartbeat semantics**: `progress` is a lease-bound liveness primitive that refreshes or records the current lease. It may carry lightweight diagnostics, but it is not a business progress percentage, checkpoint, or partial success state.
59. **Acknowledgement semantics**: `ack` is a lease-bound queue primitive that marks scheduling complete and moves the work item into terminal queue projection subject to retention. It does not define business success and must not delete or rewrite committed journal history.
60. **Negative acknowledgement semantics**: `nack` is a lease-bound queue primitive that releases or fails the current delivery attempt. Workers may provide structured retry hints, but queue policy decides whether the next state is pending, delayed, or dead-lettered.
61. **Termination semantics**: `term` is a lease-bound queue primitive that explicitly ends scheduling for a work item. It may carry a reason, but it is not business success, business failure, or a forced worker kill.
62. **Trusted queue identity**: Business-provided queue names are labels or routing hints, not trusted governance identities. Policy, quota, authorization, observability, dedupe, and replay binding use a globally unique Queue Definition ID.
63. **Structured queue scope**: Queue scope must be represented as normalized structured fields such as tenant id, workspace id, project id, and deployment id. Policy and fairness must not depend on free-form scope text.
64. **Payload reference admission**: `enqueue` validates payload reference shape, owning capability, and caller authority, but does not read the payload. Queue Worker Runtime resolves payload availability and content later through the owning service.
65. **Queue definition registry lookup**: `queueDefinitionId` must come from the platform or capability Queue Definition Registry. `enqueue` must force a registry lookup from external queue name or intent to a trusted queue definition and reject unresolved inputs rather than creating queue definitions from caller-provided names.
66. **Queue definition versioning**: Queue definitions are versioned and include trusted identity, owner capability, allowed structured scopes, default policies, retention, and delivery routes. Queue decisions that depend on definition metadata must record the adopted definition version for replay and audit.
67. **Dedupe key normalization**: Business-provided dedupe input is untrusted. The owning capability or idempotency contract must normalize or hash it into a queue-safe dedupe key before it is stored or journaled, so malformed or sensitive business identifiers do not become raw queue keys.
68. **Dedupe conflict resolution**: When normalized dedupe input maps to an existing non-terminal work item in the same queue definition and structured scope, `enqueue` returns the existing `workItemId` and scheduling summary. It must not create a duplicate work item, silently replace the existing work item, or treat normal idempotent replay as an error.
69. **Queue definition registration**: Queue definition creation or update is not hard-limited to platform deployment code. Platform, capability, or business-initiated registration is allowed, but it must go through the Queue Definition Registry and produce a versioned trusted queue definition before enqueue can target it.
70. **Unresolved queue admission**: If an external queue name or intent cannot be resolved to a registered queue definition, enqueue fails closed and the rejection is recorded in Operation or Authorization audit. No Queue Transition Journal entry is written because there is no legal queue scheduling transition.
71. **Dynamic registration policy**: Deployments may disable business-initiated dynamic queue definition registration and allow only preconfigured or otherwise governed registration paths. This is a deployment or policy setting and does not change the Work Queue Primitive Contract.
72. **Queue label uniqueness**: Queue labels are not trusted identities, but they must still be unique in the registry for operator clarity. A later registration that conflicts with an existing label is rejected and must be renamed.
73. **Queue definition lifecycle**: Queue definitions use lifecycle states such as active, disabled, and deprecated instead of immediate physical deletion. A definition must not be hard-deleted while non-terminal work items, retained journal history, snapshots, or audit requirements still reference it.
74. **Disabled definition semantics**: A disabled queue definition rejects new enqueue and new subscription or route changes. Existing work items remain governed by pause, drain, retry, and management policy rather than being deleted or implicitly canceled.
75. **Deprecated definition semantics**: A deprecated queue definition continues to process existing work items but rejects new enqueue by default unless an explicit compatibility policy allows new intake.
76. **Label rename semantics**: Queue label rename creates a new queue definition version and preserves historical alias or rename records. Replay and policy verification use queue definition identity and adopted definition version, not the current label.
77. **Delivery route versioning**: Delivery route, subscription, and worker group configuration changes must create a route version or queue definition version. New versions affect future claim and dispatch decisions only and do not mutate already leased work items.
78. **Route unavailable scheduling**: If a work item is otherwise schedulable but no valid route or worker capacity is available, the work remains pending or delayed with route-unavailable or backpressure diagnostics. It must not enter dead-letter solely because route capacity is temporarily unavailable.
79. **Route recovery scheduling**: When valid routes and capacity return, work items left pending or delayed by route unavailability naturally participate in later claim or dispatch. Route recovery does not require special work item migration.
80. **Worker capacity expiry**: Expired worker heartbeat or capacity snapshots affect only future dispatch and peer eligibility. They must not cancel, nack, or otherwise mutate already leased work items, which remain governed by lease timeout and progress.
81. **Push dispatch failure transition**: If a durable push claim succeeds but delivery to the worker fails before acceptance, the queue must immediately journal a legal dispatch failure transition and return the work item to pending or delayed. It must not rely on lease timeout as the only recovery path for undelivered push claims.
82. **Worker runtime claim boundary**: All pull and push claims originate from Queue Worker Runtime worker context. Business handlers, Tool or Console management surfaces, and arbitrary services cannot directly call the queue store claim path or impersonate workers.
83. **Requeue management boundary**: Management requeue moves eligible work back to a schedulable state through legal queue transitions. It does not directly claim work or hand work to a worker; subsequent execution still happens through Queue Worker Runtime claim.
84. **Worker binding revocation**: Revoking a worker runtime binding blocks new claims and dispatch. Existing lease-bound operations are evaluated by lease fencing and revocation policy rather than blindly accepted or unconditionally rejected.
85. **Automatic safe fallback**: Failure, timeout, crash, interruption, and delivery loss must first resolve automatically through the queue state machine into a safe scheduling state before external intervention is allowed. External actors cannot manually steer fallback while it is in progress; after the safe state is reached, they may act only through governed management operations.
86. **Safe intervention states**: External governed management may intervene only after fallback has settled work into pending, delayed, dead-letter, fallback-review, acknowledged, or terminated state. Leased work must not be manually rewritten while automatic fallback is still resolving it.
87. **Fallback journal requirement**: Automatic fallback transitions must be journaled with reason, trigger source, adopted time, policy version, and adopted target state. Replay verifies recorded fallback decisions rather than recreating them from live worker or clock state.
88. **Fallback subtask execution**: Each automatic fallback flow runs as an independent lightweight async subtask or coroutine. A fallback coordinator manages state outside the coroutine, prevents duplicate or overlapping fallback attempts, and records completion or failure so fallback execution itself can be recovered safely.
89. **Durable fallback coordinator state**: The fallback coordinator must persist fallback task identity, work item identity, source transition, state, attempts, lock or fencing token, and last error so process restart does not lose in-progress fallback work.
90. **Fallback review state**: If a fallback subtask fails after bounded retries, the work item enters `fallback_review` or an equivalent safe review state instead of remaining leased. This state is queue-internal and does not classify the business task as failed.
91. **Fallback fencing lock**: At most one fallback subtask may mutate a given work item at a time. Lease expiry, worker crash, dispatch failure, interruption, and other fallback sources must use a per-work-item lock or fencing token to prevent competing fallback transitions.
92. **Fallback review operations**: `fallback_review` allows only governed operations such as inspect, retry fallback, move to dead-letter, terminate scheduling, or requeue through legal transitions. Workers cannot directly claim work from fallback review.
93. **Fallback retry policy**: Fallback subtask retry attempts, backoff, adopted delay, and exhaustion behavior are controlled by queue policy. Fallback retry decisions must record policy version, attempts, and adopted timing before they affect coordinator state or work item state.
94. **Unified background write aspect**: Fallback coordinator state and related background queue storage must persist through the queue's unified background write aspect or port, stored with the queue store and linked to transition journal entries. Background writes may be asynchronous where semantics allow, but queue components must not implement scattered direct writes that bypass the aspect or make future database migration harder.
95. **Background write ordering**: Background writes for the same work item must be serialized according to journal or transition order. Fallback, snapshot, compaction, and coordinator writes must not reorder state for a work item.
96. **Background write retry**: Asynchronous background write failures may retry silently before entering an observable internal health or review state, but retry count, backoff, and exhaustion behavior are versioned policy decisions and must not be hidden infinite retry or silent discard.
97. **Storage adapter migration boundary**: Replacing SQLite with another database changes Work Queue Store Adapter and Queue Background Write Aspect implementations only. Fallback, worker runtime, management, policy, and upper-layer code must not directly adapt to concrete database APIs.
98. **Internal health boundary**: Queue internal health is infrastructure operations state for the store, background write aspect, daemon, fallback coordinator, replay, snapshot, and compaction behavior. It may gate scheduling, trigger protective pause, or expose read-only inspection, but it is not work item scheduling state and must not write business state.
99. **Protective pause on persistence risk**: When background writes, queue store, replay, fallback, or related persistence paths fail beyond the adopted policy threshold, the queue should enter protective pause for the affected queue, scope, subscription, or store boundary. Protective pause prevents new unsafe queue mutations while preserving inspection and recovery paths.
100. **Automatic recovery before manual governance**: Queue internal health degradation should first trigger automatic recovery, such as retrying background writes, rebuilding projections, resuming safe coordinator tasks, checkpointing or recovering WAL state, and shedding load under protective pause. Manual governance is reserved for exhausted automatic recovery so queue congestion does not wait on slow human intervention.
101. **Recovery memory guard**: Automatic recovery must enforce hard memory and backlog thresholds. If recovery pressure exceeds adopted limits, the queue rejects new enqueue or escalates protective pause instead of growing unbounded in memory.
102. **Recovery success proof**: Protective pause can be cleared only after automatic recovery proves background writes are healthy, projections validate against journal and snapshots, fallback coordinator tasks are accounted for, and the journal can continue appending safely.
103. **Recovery failure report**: If automatic recovery exhausts, the queue emits a structured recovery report with affected queue definitions, scopes, subscriptions, last successful journal offset, failed component, error summaries, adopted policy versions, and recommended governed actions.

## Consequences
- Pact can use NATS JetStream as a reference implementation source without binding upper layers to NATS terminology or runtime dependencies.
- Queue storage can be optimized for single-node SQLite WAL while preserving a stable migration path to other durable stores.
- The queue remains a platform infrastructure primitive instead of becoming a business job manager or workflow engine.
- Journal retention, compaction, and archive operations become governed platform concerns rather than hidden storage cleanup tasks.
- Application capabilities must migrate queue usage through handlers and references rather than carrying their own durable scheduling cores.
- Existing JobManager file-backed metadata can remain a business artifact during migration, but not as the new queue scheduling source of truth.
- Queue auditability is achieved through minimized scheduling evidence and references, not by copying payloads or business results into the queue journal.
- External brokers can be adopted later without turning broker-native streams, consumers, subjects, or retention policies into Pact platform contracts.
- Queue store upgrades and external API exposure become governed compatibility events, not incidental implementation details.
- Queue implementation code must centralize time, identity generation, and storage optimization so replay, testing, and production durability stay controllable.
- Queue identity, scope, and payload references are normalized before scheduling so untrusted business labels and payload contents do not become hidden policy inputs.
- Queue definition lookup and dedupe normalization make enqueue admission fail closed when business inputs are unknown, malformed, or inconsistent.
- Queue definition registration is extensible, but queue usage still depends on registry resolution rather than implicit creation from enqueue input.
- Queue labels remain operator-facing and unique, while trusted scheduling and governance bind to queue definition identities and versions.
- Queue recovery and fallback behavior is automatic and state-machine owned; operators intervene only after work has reached a safe scheduling state.
- Fallback execution is isolated into recoverable subtasks so crash, timeout, delivery, and interruption recovery do not collapse into a single unmanaged background loop.
- Fallback failures have their own safe review state and durable coordinator records, preventing leased work from becoming permanently stuck.
- Background queue persistence flows through a unified write aspect so fallback, snapshot, compaction, and coordinator writes remain migratable to future database adapters.
- Background write failures can be retried quietly under versioned policy, but exhausted persistence failures become observable internal queue health issues.
- Queue health degradation first enters automatic recovery and protective gating so persistence failures do not grow unbounded in memory while waiting for manual governance.
- Automatic recovery must prove success or emit structured failure evidence before manual governance takes over.
- Implementations must pay the cost of append-only transition tracing, projection rebuild, and randomized state-machine verification before being treated as production-ready.
