# Server Web Frontend Architecture Audit (2026-06-01)

## Scope

This audit covers the current `server-web` Vue console implementation:

- `server-web/components`
- `server-web/composables`
- `server-web/views`
- `server-web/styles`
- `server-web/lib`
- `server-web/i18n`
- `server-web/router`
- `server-web/types`

The `CLIENT_*` documents describe the destructive desktop client refactor, not a direct replacement plan for the server console. For `server-web`, the active architectural boundary is `docs/Architecture.md`: the Vue console may enter the service layer only through `bridge`, `/api/*`, event subscriptions, and controlled download URLs; page-level UI should reuse shared components from `server-web/components/common.ts` before private per-view controls are added.

## Assessment Criteria

Line count is only a risk signal, not the refactor objective. A file becomes a priority when its size also correlates with unstable state ownership, mixed side effects, unclear API/type contracts, broad CSS scope, duplicated rendering decisions, or poor verification isolation.

Current frontend changes should therefore be judged against these criteria:

- State ownership: route pages should provide context and orchestration; domain controllers should own async workflow state; presentational components should avoid hidden workflow side effects.
- Coupling: child components may use route-local context when they are feature-private, but reusable primitives should use props/emits and typed inputs.
- Side effects: bridge calls, timers, browser APIs, downloads, storage, and polling should stay in domain helpers or controllers, not scattered through templates.
- Styling scope: extracted components must preserve visual behavior without leaking broad selectors across unrelated routes.
- Type contracts: split modules should preserve explicit domain types and avoid moving `any` or stringly payload assumptions into more places.
- Verification: every refactor should pass architecture gates, feature registry checks, typecheck, a raw renderer build, and a browser smoke on affected routes.

### Direct Coupling Hotspots

Direct `useConsole()` callers:

- `server-web/composables/useServerConsoleShell.ts`

Leaf view direct `useConsole()` callers are now zero. Page facades and feature controllers consume `serverConsoleShellContext`, route-local contexts, or nested shell domain contexts such as `feedConsole`, `debugConsole`, `knowledgeDomainConsole`, `approvalFlowConsole`, and `toolManagementConsole`. The only remaining direct `useConsole()` caller is the shell composition boundary, enforced by `npm run server:verify:frontend-architecture`.

Direct `bridge.*` calls from view/component files:

- `server-web/components/BridgeDownloadButton.vue` - 1 allowed component-level bridge boundary for controlled downloads.

Direct `bridge.*` calls from composables and `server-web/lib` domain helpers are now zero. Feature controllers call focused API clients directly, while `bridge.ts` remains a compatibility facade for older external call signatures.

`v-html` sites:

- `server-web/components/SafeHtmlBlock.vue`

Page-level HTML rendering now goes through `SafeHtmlBlock`, which requires callers to declare whether the content came from `markdownToSafeHtml` or `renderEvidenceReadableHtml`. The remaining `v-html` surface is therefore a single explicit rendering boundary instead of duplicated page-level trust assumptions.

## P0 Issues

### P0-1: `useConsole.ts` is still the cross-page frontend runtime


Knowledge page injection now follows the same narrow-context direction: `useKnowledgeViewConsole.ts` returns focused page/ingest/library/maintenance/rules/word-cloud groups, and `knowledgeViewContext.ts` provides those groups separately so knowledge leaf components no longer receive one broad all-fields view context.

Knowledge distillation workbench run/list/action state remains in `knowledge-distillation-workbench-controller.ts`, while model selection normalization, probe labels/status, probe API calls, and delayed probe timers live in `knowledge-distillation-model-probe-controller.ts`.

Required direction:

- Keep `useConsole()` temporarily as a compatibility shell only.
- Move remaining page/domain state into cohesive controllers or contexts: shell, auth compatibility, settings/model library, runtime/admin state, production health, knowledge management, knowledge distillation, workspaces, debug, and admin permissions.
- Leaf views should continue consuming route/domain contexts, not import `useConsole()` directly.
- The next extraction wave should split the singleton internals behind the audited shell/domain contexts, continuing with remaining admin route templates such as Tools, runtime/admin state, and any newly emerging agent-explore orchestration internals that still prevent `useConsole()` from becoming a pure compatibility facade.

### P0-2: UI files call `bridge` directly instead of domain controllers

The remaining view/component bridge call is `BridgeDownloadButton.vue`, which is the controlled download exception. `KnowledgeDistillationWorkbench.vue`, `AgentPermissionsView.vue`, `RuntimeDownloadsView.vue`, `ProductionHealthView.vue`, `KnowledgeView.vue`, and `KnowledgeImportCard.vue` have been moved behind domain/helper modules, which should be the pattern for future direct callers.

Required direction:

- Move direct bridge calls into domain composables or `server-web/lib/*` domain clients.
- Components should receive callbacks/state or use feature controllers.
- Keep `BridgeDownloadButton.vue` as the exception for the already-standardized controlled download bridge.

### P0-3: Large feature components mix rendering, workflow state, and side effects

The original 500+ line Vue page/component templates have been reduced below the P0 threshold. Production health, feed, debug, sources, Agent Config, Agent Config model-entry cards, Agent Permissions, authorization governance, Storage overview, Maintenance Agent, Ops Monitor, Runtime Modules, Runtime Downloads, word-cloud, knowledge rules, workspace detail, workspace expanded detail, history/session list rendering, shell side navigation, and shared agent model option selection now stay under focused composition, local-context, projection-helper, or style-slice boundaries. No Vue route/component template currently sits on the 300-line edge; keep monitoring new growth and split any file that approaches that threshold.

Required direction:

- Split feature state and async operations into composables.
- Split repeated visual regions into focused child components only when the child has a clear domain responsibility.
- Keep UI components declarative: props, emits, and simple local visual state.

### P0-4: Styling is globally large and hard to reason about

The CSS layer no longer has 500+ line shared or view-level monoliths. `features.css`, `components.css`, `themes.css`, `layout.css`, and the largest view style groups are now import facades over focused slices, including debug agent explore, word cloud, knowledge sources, info feed flow, knowledge maintenance, admin runtime/tools, drawer/path dialogs, admin maintenance, shell/knowledge search, and shared responsive rules. The remaining CSS risk is now in mid-sized slices such as `model-library.css`, `word-cloud/class-cards.css`, `info-feed-inputs.css`, and `features/panels.css`; these are below the old P0 threshold but still worth watching as feature ownership evolves.

Required direction:

- Maintain the CSS facade guards and keep future style additions in the owning token, primitive, component, or view slice.
- Move repeated component primitives into shared component classes or component-local CSS.
- Keep view-specific selectors under clear route namespaces.
- Avoid broad restyling until ownership boundaries are split.

## P1 Issues

### P1-1: Safe HTML rendering boundary is now centralized

Feed summaries, debug answers, and evidence previews now use `SafeHtmlBlock`. The component preserves existing sanitized and sandboxed renderer output while making the source contract explicit at each call site.

Remaining direction:

- Move from string props to typed render results if the renderer layer grows beyond the current `markdownToSafeHtml` and `renderEvidenceReadableHtml` sources.
- Move CSS class ownership into the component where possible after the evidence/feed styles are split.

### P1-2: Browser effects are scattered

`window`, `document`, local storage, timers, DOM query/highlight, clipboard, direct bubbles, and confirms are spread across controllers and views.

Agent-explore split-pane dragging and system-log column resizing now share `console-pointer-drag-controller.ts`, which owns document-level pointer listeners, pointer cancel cleanup, and body cursor/user-select restoration. Upload split-button click-outside and Escape handling now share `console-document-dismiss-controller.ts`, so the upload menu component no longer owns global document listener lifecycle directly. Confirmation dialogs, alert notifications, config-target DOM query/highlight/scroll, feature data-anchor scrolling, clipboard copy, text-file export, and floating copy feedback now flow through `console-browser-effects.ts`; Workspaces no longer builds its own DOM bubble, tool-token copy no longer calls `navigator.clipboard` directly, destructive confirmations in jobs, workspaces, tool grants, permission groups, settings save, and the distillation workbench share one browser-effect boundary, and both bridge-mediated downloads plus console text exports use the shared `browser-downloads.ts` object-URL lifecycle. Agent-explore polling, Codex OAuth polling, source-list polling, refresh throttling, knowledge-distillation run/model-probe timers, server-event retry/next-run delays, info-feed summary streaming delays, debug distillation polling delays, and info-feed fetch-retry delays now share `console-timer-controller.ts`, so those controllers own workflow decisions without hand-rolling interval/timeout cleanup. Page-refresh dispatch/listener wiring now uses `console-window-event-channel.ts`, so feature handlers depend on a typed event channel instead of direct `window` event lifecycle. Hash-route navigation, Codex OAuth popup launch, browser-origin lookup, URL base parsing, and localStorage access now route through `server-web/lib/browser-window.ts`, while localStorage JSON cache parsing/stringifying now routes through `server-web/lib/browser-storage.ts`; info-feed history and agent-explore persistence now write versioned cache payloads, preserve legacy-cache restore, and cap history/id-list growth before persistence.

Required direction:

- Continue moving common browser effects into small utilities, with remaining emphasis on documenting the remaining dedicated browser-state/config-target boundaries and adding focused tests around cache migrations.
- Keep per-feature controllers responsible for workflow decisions, not raw DOM manipulation.

### P1-3: Route contexts exist but are not consistently used

`serverConsoleShellContext.ts`, `knowledgeViewContext.ts`, `workspacesViewContext.ts`, `feedViewContext.ts`, `debugViewContext.ts`, `agentRetrievalViewContext.ts`, `modulesViewContext.ts`, `sourcesViewContext.ts`, and `agentPermissionsViewContext.ts` are present. Leaf views and page facades now use contexts instead of importing `useConsole()` directly. `feedViewContext.ts`, `debugViewContext.ts`, `agentRetrievalViewContext.ts`, `modulesViewContext.ts`, and `sourcesViewContext.ts` expose explicit feature boundaries, with agent retrieval now split into answer/form/page/progress/tabs/trace/workspace groups; the shell context exposes explicit nested domain contexts instead of the full upstream singleton or a flat compatibility whitelist.

Required direction:

- Keep route-level providers as the default way to pass shell/page state.
- Add missing admin/debug contexts where the page has multiple child views.
- Narrow the shell return surface so route contexts stop inheriting the full singleton.

### P1-4: Type looseness remains in shared utilities

`any` appears in the Workspaces facade/client boundary, the Cloud Drive controller/client boundary, model utilities, table header drag events, and selected evidence metadata paths. Word-cloud utility callbacks now use typed `KnowledgeWordCloudTerm` data instead of loose `any`, recall payload projection no longer uses loose casts, and workspace endpoint payload looseness is increasingly isolated behind `workspaces-client.ts` plus focused Workspaces controllers instead of mixed with page-level request mechanics.

Required direction:

- Replace generic `any` with domain types from split type modules.
- Keep `DataTable.vue` generic only where the component boundary genuinely requires it.

### P1-5: Console i18n catalog data is split from the runtime

`server-web/i18n/console.ts` is now a 13-line public facade. Locale state lives in `console-locale-state.ts`, text translation lives in `console-text-localizer.ts`, and dynamic regex localization is a 25-line `console-dynamic-patterns.ts` facade over count/metric and status/message slices. Structured messages live in `server-web/i18n/console-messages.ts`, `server-web/i18n/console-phrases.ts` is a 16-line facade, and static phrase/segment replacement data lives under `server-web/i18n/console-phrases/*` with shared tuple typing in `console-phrase-types.ts`. DOM mutation/localization behavior remains in `server-web/i18n/console-dom-localizer.ts`. The remaining catalog risk is growth inside the largest phrase slice, `console-phrases/ops-production.ts` at 373 lines, rather than a mixed root catalog.

Required direction:

- Keep phrase catalog additions in the owning shell/core, debug, knowledge, governance/workspaces/feed, ops/production, or segment slice; split `ops-production.ts` again if it crosses a cohesive ownership boundary.
- Keep dynamic regex additions in the owning count/metric or status/message pattern slice, not in the public facade or text localizer.
- Keep DOM localization runtime in `server-web/i18n/console-dom-localizer.ts` and avoid moving browser lifecycle code back into the catalog.
